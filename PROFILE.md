<a id="planejamento-de-um-cluster-novo"></a>

### Planning a new cluster

Before creating a cluster, Guilherme starts by understanding the **product and the problem to solve**, including whether Kubernetes is actually necessary.

Technical planning includes:

- Understand the product context through a briefing/kickoff.
- Map the number of services that will run in the cluster.
- Estimate pod counts per service.
- Choose the cloud/runtime environment.
- Assess persistence and storage needs.
- Define how traffic will enter the cluster.
- Evaluate **NLB or ALB** as appropriate.
- Consider reproducibility through **Infrastructure as Code** from the outset.
- Consider **Terraform/Terragrunt** to create and replicate infrastructure.
- Define the environment strategy, such as Dev/Staging/Prod.
- Decide between isolation through **namespaces** and multiple clusters.
- Structure the required manifests/resources, including **Ingress, Services, Deployments, HPA and ConfigMaps**.

The reported approach is to **plan cluster architecture and organization first**, then implement.

<a id="upgrade-de-clusters"></a>

### Cluster upgrades

- Led multiple Kubernetes/EKS upgrades, responsible for research, documentation, execution planning and technical execution.
- Before upgrading, identifies version changes and breaking changes and documents their impact and solutions.
- For larger changes, validates in development first and records problems and how they were resolved.
- In production, assesses downtime and maintenance needs; the window is aligned with management/business stakeholders.
- For critical upgrades, prefers cluster replacement/blue-green rather than relying on a downgrade: keeps the old cluster available, builds and validates the new one, and redirects traffic/DNS; on failure, restores the pointer to the previous cluster.
- Executes the procedure and trains junior DevOps engineers to perform it, turning knowledge into reusable documentation/playbooks.
- One incompatibility encountered involved NGINX/load balancer annotations/settings affecting parameters such as body size; the fix was investigated and added to the playbook.

<a id="requests-limits-e-tuning"></a>

### Requests, limits and tuning

- CPU/memory sizing is informed by APM, load tests and observed application behavior.
- Considers minimum startup consumption, normal consumption and peaks; uses technical judgment to choose between more resources per pod and spreading load across more replicas.
- Avoids permanently oversizing an application solely for occasional peaks.

<a id="troubleshooting-de-pods"></a>

- After eliminating local causes, broadens the investigation to abnormal traffic/requests and external factors, including possible DDoS attacks.

- Guilherme created the first pipelines, introduced Git Flow, documented standards and trained developers individually.
- Evolution was incremental: stabilize build/deploy first, then incorporate controls such as SonarQube, Trivy, Semgrep and GitLeaks.
- Improvement is iterative: experiment, gather feedback, fix what needs changing and preserve standards that work.

<a id="configuracao-e-aplicacoes-stateless"></a>

### Configuration and stateless applications

- One of the first structural changes was removing hard-coded application configuration.
- Frontend URLs that had previously been changed manually before each build moved into configuration/environment variables.
- The approach extended to the backend, replacing local file/configuration dependencies with environment variables and standardized conventions.
- Created naming conventions, such as database prefixes (`DB_USER`, `DB_DATABASE`, etc.), reducing variation across applications.

<a id="governanca-e-adesao"></a>

### Governance and adoption

- Combines technical persuasion and governance: decisions are open to discussion, while standards considered essential for security, consistency and operations are treated as non-negotiable.

### Reuse and shared pipelines

- Earlier, when the CI/CD platform lacked suitable shared pipelines, some configuration duplication was unavoidable.

- Commit messages also included the task identifier, supporting Git/Jira traceability.

<a id="seguranca--aprofundamento"></a>

<details>
<summary><strong>Security — detailed review</strong></summary>

<a id="modelagem-de-acesso"></a>

### Access design

- Before granting access, identifies **which permission is needed and who will receive it**.
- For one-off, highly specific access, may use a user with an inline policy restricted to the required resource.
- When permissions are likely to evolve, be maintained or be reused, prefers a separate manageable policy, applying the **principle of least privilege**.
- Before creating a custom policy, checks whether an existing managed policy meets the need.
- Structures custom policies for reuse while avoiding overly broad permissions.
- Groups shared permissions for multiple users/services with common needs to reduce repetitive individual grants.

<a id="revisao-e-remocao-de-acessos"></a>

### Access review and removal

- Removes access through user offboarding and service decommissioning checklists.
- Reviews recent credential/key activity as evidence of use.
- Does not remove access solely because a credential has been unused for a while; requires contextual validation and confirmation that access is no longer needed.

<a id="oidc-e-credenciais"></a>

### OIDC and credentials

- Uses **OIDC in pipelines** to avoid dependence on static AWS keys.
- Already uses **Secrets Manager** and periodic rotation of sensitive credentials.

<a id="prioridades-para-avaliacao"></a>

### Evaluation priorities

1. **Cost and ROI — the main priority.** Products operate with tight returns; cost increases need strong justification and an appropriate expense/benefit relationship. Cost is a strong architectural constraint.
